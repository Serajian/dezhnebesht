# طراحی: ذخیره‌ی پیشرفت نقشه‌ی راه با ایمیل

تاریخ: ۲۰۲۶-۱۰-۰۶

## هدف

پیشرفت نقشه‌ی راه (کدام مدخل‌ها خوانده شده) امروز فقط در `localStorage` همان مرورگر است و با عوض کردن مرورگر یا دستگاه از دست می‌رود. هر کس باید بتواند با زدن ایمیل خودش این پیشرفت را روی سرور نگه دارد و در دستگاه دیگری با همان ایمیل پس بگیرد.

معیار موفقیت: نه پیاده‌سازی چیز عجیبی داشته باشد، نه ورود برای کاربر. یک فیلد ایمیل، یک دکمه، تمام.

## تصمیم‌های گرفته‌شده

- **ایمیل فقط شناسه است، بدون تأیید.** نه لینک جادویی، نه کد یک‌بارمصرف، نه رمز. داده حساس نیست (فهرست شناسه‌ی مدخل‌های خوانده‌شده) و هزینه‌ی سرویس ارسال ایمیل و پیچیدگی ورود برایش نمی‌ارزد. پیامد پذیرفته‌شده: هر کس ایمیل کسی را بداند می‌تواند پیشرفت او را ببیند یا عوض کند.
- **SQLite با ماژول داخلی `node:sqlite`.** بدون بسته‌ی npm، پس قانون «بدون وابستگی» پروژه نمی‌شکند. Node 22 آن را بدون flag اجرا می‌کند و فقط یک `ExperimentalWarning` چاپ می‌کند.
- **همان `serve.js`، همان کانتینر.** سرویس دوم یا Postgres برای این حجم داده سنگین است. فایل JSON به‌جای دیتابیس با نوشتن هم‌زمان یا کرش وسط نوشتن خراب می‌شود؛ SQLite این را رایگان حل می‌کند.

## معماری

```
serve.js              فایل ایستا مثل قبل؛ مسیرهای /api/ را به server/api.js می‌دهد
server/
  api.js              مسیرها، محدودیت نرخ، خواندن بدنه؛ تنها جایی که node:sqlite را import می‌کند
  progress-store.js   باز کردن دیتابیس، ساخت جدول، get/put
assets/js/
  sync.js             منطق محض: normalize و اعتبارسنجی ایمیل، اعتبارسنجی بدنه، ادغام union
  account.js          DOM و fetch: پنل ورود، همگام‌سازی با سرور
```

`sync.js` بدون DOM و بدون شبکه است، مثل `roadmap.js`، تا هم مرورگر و هم سرور (`server/api.js`) آن را import کنند و یک تعریف از «ایمیل معتبر» و «بدنه‌ی معتبر» در دو طرف باشد. `node --test` آن را مستقیم پوشش می‌دهد.

### داده

یک جدول:

```sql
CREATE TABLE IF NOT EXISTS progress (
  email      TEXT NOT NULL,
  topic_id   TEXT NOT NULL,
  read_ids   TEXT NOT NULL,   -- همان رشته‌ی JSON که serializeProgress می‌سازد
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (email, topic_id)
);
```

قالب `read_ids` همان قالب `localStorage` است، پس هیچ تبدیلی بین دو طرف لازم نیست. مسیر فایل از متغیر محیطی `DB_PATH` می‌آید. اگر `DB_PATH` تنظیم نشده باشد (مثلاً `node serve.js` محلی بدون تنظیم)، API خاموش است و `/api/health` ۴۰۴ می‌دهد؛ سایت مثل امروز کار می‌کند.

ایمیل پیش از هر استفاده normalize می‌شود: `trim` و `toLowerCase`. ایمیل معتبر یعنی حداکثر ۲۵۴ کاراکتر، دقیقاً یک `@`، بخش محلی و دامنه‌ی ناخالی، و یک `.` در دامنه. چیزی بیش از این چک نمی‌شود؛ ایمیل تأیید نمی‌شود و نیازی هم به دقت RFC نیست.

### API

| مسیر | کار |
|---|---|
| `GET /api/health` | `200 {"ok":true}` — مرورگر با آن می‌فهمد ورود در دسترس است |
| `GET /api/progress?email=…` | `200 {"<topicId>": ["id", …], …}` — همه‌ی موضوع‌های آن ایمیل؛ ایمیل ناشناخته `{}` می‌دهد، نه ۴۰۴ |
| `PUT /api/progress` | بدنه `{"email", "topicId", "readIds": [...]}` — جایگزین کامل آن ردیف؛ پاسخ `204` |

اعتبارسنجی:

- ایمیل نامعتبر → `400`.
- `topicId` باید رشته‌ی ناخالی تا ۶۴ کاراکتر باشد → وگرنه `400`.
- `readIds` باید آرایه‌ی رشته باشد، هر رشته تا ۱۲۸ کاراکتر، حداکثر ۵۰۰۰ عضو → وگرنه `400`.
- بدنه‌ی بزرگ‌تر از ۶۴KB → `413`، بدون خواندن بقیه.
- متد دیگر روی مسیر API → `405`.

سرور شناسه‌ها را با داده‌های `data/` مقایسه نمی‌کند. شناسه‌ی ناشناخته بی‌ضرر است و `parseProgress` در مرورگر هم فقط رشته‌ها را نگه می‌دارد.

### محدودیت نرخ

شمارنده‌ی درون‌حافظه به‌ازای هر IP، پنجره‌ی ثابت یک‌دقیقه‌ای، ۶۰ درخواست؛ بیشتر از آن `429`. IP از اولین مقدار `X-Forwarded-For` خوانده می‌شود، چون سایت پشت Traefik ِ Dokploy است، و اگر نبود از `socket.remoteAddress`. شمارنده‌ها هر دقیقه دور ریخته می‌شوند تا حافظه رشد نکند. این فقط جلوی امتحان انبوه ایمیل‌ها را می‌گیرد، نه حمله‌ی جدی؛ با ری‌استارت کانتینر صفر می‌شود و اشکالی ندارد.

## مرورگر

### پنل ورود

- یک `chrome-icon-btn` تازه در هدر، کنار دکمه‌های پوسته و زبان، با آیکون SVG درون‌خطی.
- **فقط وقتی دیده می‌شود که `GET /api/health` موفق باشد.** روی GitHub Pages این درخواست ۴۰۴ می‌دهد و دکمه هرگز ظاهر نمی‌شود.
- کلیک یک پنل کوچک باز می‌کند (نه modal تمام‌صفحه): یک فیلد ایمیل با `dir="ltr"` و `type="email"`، و دکمه‌ی «ذخیره‌ی پیشرفت». پس از ورود، پنل ایمیل جاری و دکمه‌ی «خروج» را نشان می‌دهد.
- همه‌ی متن‌ها دوزبانه‌اند و به جدول‌های کلید `i18n.js` اضافه می‌شوند، پس تست کلیدهای i18n آن‌ها را هم پوشش می‌دهد.
- ایمیل ورودی در `localStorage` با کلید `dezhnebesht:account` نگه داشته می‌شود.

### همگام‌سازی

- `localStorage` منبع اصلی می‌ماند. بدون ورود، همه‌چیز دقیقاً مثل امروز است.
- **هنگام ورود:** `GET` پیشرفت سرور، برای هر موضوع اجتماع (union) آن با پیشرفت محلی، نوشتن نتیجه در `localStorage`، و `PUT` هر موضوعی که نتیجه‌اش با سرور فرق دارد. هیچ تیکی از هیچ طرف گم نمی‌شود.
- **هنگام بارگذاری صفحه با ایمیل ذخیره‌شده:** همان ادغام، تا تیک‌های دستگاه دیگر برسد.
- **هر تیک یا برداشتن تیک:** `saveProgress` مثل امروز محلی می‌نویسد، سپس اگر وارد شده‌ایم `PUT` آن موضوع با debounce حدود ۸۰۰ میلی‌ثانیه به‌ازای هر موضوع، تا تیک‌های پشت‌سرهم یک درخواست بسازند.
- **بازنشانی پیشرفت** (دکمه‌ی موجود) هم یک `PUT` با آرایه‌ی خالی است. محدودیت پذیرفته‌شده: اگر دستگاه دیگری هنوز تیک‌های قدیمی را محلی دارد، بارگذاری بعدی آن دستگاه با union آن‌ها را برمی‌گرداند. برای نگه داشتن سادگی، حذف بین دستگاه‌ها همگام نمی‌شود.
- **خروج:** فقط کلید `dezhnebesht:account` پاک می‌شود. پیشرفت محلی می‌ماند.

### خطاها

هر خطای شبکه یا پاسخ غیر ۲xx در مرورگر بی‌صدا رد می‌شود: پیشرفت محلی ذخیره شده و سایت از کار نمی‌افتد. تنها خطایی که به کاربر نشان داده می‌شود ایمیل نامعتبر در فیلد ورود است، که پیش از ارسال با همان تابع `sync.js` چک می‌شود. همه‌ی دسترسی‌های `localStorage` مثل امروز در try/catch اند.

## دیپلوی

`Dockerfile`:

- `COPY server/ ./server/` در کنار بقیه.
- `ENV DB_PATH=/data/progress.db`.
- ساخت `/data` با مالکیت کاربر `node` پیش از `USER node`.

در Dokploy یک کار دستی لازم است: در Mounts سرویس، یک **Volume** با مسیر `/data`. بدون آن دیتابیس با هر دیپلوی پاک می‌شود. پشتیبان یعنی کپی همان یک فایل.

`CLAUDE.md` و `README.md` به‌روز می‌شوند: ورود فقط روی VPS کار می‌کند، روی GitHub Pages پنهان است، و volume لازم است. جمله‌ی «Local serving is identical to what GitHub Pages runs» دیگر کامل درست نیست و اصلاح می‌شود.

## تست

همه با `node --test`، بدون بسته:

- `test/sync.test.mjs`: normalize و اعتبارسنجی ایمیل (حروف بزرگ، فاصله، بدون `@`، دو `@`، بیش از ۲۵۴ کاراکتر)، اعتبارسنجی بدنه (هر مرز بالا)، و ادغام union (خالی، هم‌پوشان، موضوعی که فقط در یک طرف است).
- `test/api.test.mjs`: `serve.js` را با `DB_PATH` موقت در یک پوشه‌ی موقت و پورت تصادفی بالا می‌آورد و این‌ها را امتحان می‌کند: health؛ PUT سپس GET رفت‌وبرگشت؛ ایمیل با حروف بزرگ همان ردیف را می‌خواند؛ ایمیل ناشناخته `{}`؛ ورودی بد `400`؛ بدنه‌ی بزرگ `413`؛ متد غلط `405`؛ و درخواست ۶۱ام `429`. یک مورد هم بدون `DB_PATH` بالا می‌آورد و `404` را روی health چک می‌کند.
- پنل ورود در مرورگر دستی امتحان می‌شود: یک بار با `DB_PATH` (ورود، تیک، ورود از پنجره‌ی خصوصی دیگر) و یک بار بدون آن (دکمه دیده نمی‌شود).

## بیرون از این طراحی

تأیید ایمیل، حساب کاربری، رمز، حذف حساب از طریق رابط، همگام‌سازی ترجیحات دیگر (پوسته، زبان، گروه‌ها)، و همگام‌سازی حذف بین دستگاه‌ها.
