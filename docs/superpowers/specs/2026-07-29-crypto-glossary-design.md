# طراحی: دانشنامه شخصی کریپتو و بلاکچین

تاریخ: ۲۰۲۶-۰۷-۲۹

## هدف

یک وب‌سایت ایستا که به عنوان دانشنامه و واژه‌نامه‌ی شخصی کار می‌کند. محتوا به **موضوع** تقسیم می‌شود (کریپتو و بلاکچین موضوع اول است) و هر موضوع دسته‌ها و مدخل‌های خودش را دارد. صفحه‌ی اصلی فهرست اصطلاحات قابل کلیک به‌علاوه‌ی نوار جستجوست؛ کلیک روی هر اصطلاح صفحه‌ی آن را باز می‌کند.

روند استفاده: کاربر هر بار مطلبی می‌خواند، آن را شرح می‌دهد و مدخل متناظرش به داده‌ها اضافه می‌شود. پس **کم‌هزینه بودنِ افزودن یک مدخل، مهم‌ترین معیار موفقیت این طراحی است.**

نهایتاً روی GitHub Pages (ریپوی public) منتشر می‌شود.

## محدودیت‌ها

- بدون فریم‌ورک، بدون بسته‌ی npm، بدون مرحله‌ی build. HTML، CSS و JS خام.
- بدون درخواست به دامنه‌های خارجی: بدون CDN، بدون فونت آنلاین. سایت باید کاملاً مستقل بالا بیاید.
- داده‌ها با `fetch()` از فایل‌های JSON خوانده می‌شوند. این یعنی باز کردن مستقیم `index.html` با `file://` کار **نمی‌کند** و همیشه به یک سرور نیاز است (محلی یا GitHub Pages).

## ساختار فایل‌ها

```
index.html              اسکلت صفحه؛ بدون محتوای مدخل‌ها
serve.js                سرور استاتیک محلی، بدون وابستگی
assets/
  css/style.css
  js/
    data.js             لود فایل‌های داده + اعتبارسنجی
    i18n.js             زبان جاری و متن‌های رابط کاربری
    search.js           جستجو و فیلتر هشتگ
    render.js           ساخت نمای فهرست و نمای مدخل
    router.js           مسیریابی hash
    app.js              اتصال ماژول‌ها
data/
  topics.json           فهرست و ترتیب موضوع‌ها
  <topic>/
    categories.json     دسته‌های آن موضوع
    entries/
      <category>.json   مدخل‌های هر دسته
```

ماژول‌های JS با `<script type="module">` لود می‌شوند.

هر ماژول یک مسئولیت دارد و از طریق export مشخص با بقیه حرف می‌زند:

| ماژول | ورودی | خروجی |
|---|---|---|
| `data.js` | — | `loadAll()` که آرایه‌ی مدخل‌ها و دسته‌ها را برمی‌گرداند، و گزارش اعتبارسنجی |
| `i18n.js` | زبان انتخابی | `t(key)` برای متن‌های رابط، `current()`، `set(lang)` |
| `search.js` | آرایه‌ی مدخل‌ها، عبارت جستجو، هشتگ فعال | آرایه‌ی فیلترشده |
| `render.js` | مدخل یا آرایه‌ی مدخل | المان DOM |
| `router.js` | — | رویداد تغییر مسیر با پارامترهای تجزیه‌شده |

`render.js` نباید داده لود کند و `data.js` نباید DOM بسازد.

## مدل داده

### `data/topics.json`

```json
[
  { "id": "crypto",   "fa": "کریپتو و بلاکچین", "en": "Crypto & Blockchain" },
  { "id": "security", "fa": "شبکه و امنیت",     "en": "Networks & Security" }
]
```

ترتیب موضوع‌ها در فهرست، همان ترتیب این آرایه است. `id` نام پوشه‌ی موضوع زیر `data/` است.

**افزودن یک موضوع:** یک پوشه با `categories.json` و `entries/` بساز و یک سطر به این فایل اضافه کن. هیچ فایل JS‌ای دست نمی‌خورد.

### `data/categories.json`

```json
[
  { "id": "basics",    "file": "basics.json",    "fa": "مفاهیم پایه", "en": "Fundamentals" },
  { "id": "consensus", "file": "consensus.json", "fa": "اجماع",       "en": "Consensus" }
]
```

ترتیب دسته‌ها در فهرست، همان ترتیب این آرایه است.

### `data/entries/<category>.json`

```json
[
  {
    "id": "proof-of-work",
    "tags": ["mining", "consensus", "bitcoin"],
    "related": ["hash", "nonce"],
    "svg": "<svg …>…</svg>",
    "fa": {
      "title": "اثبات کار",
      "short": "تعریف یک‌خطی که در فهرست زیر نام دیده می‌شود",
      "body": "<p>توضیح کامل، می‌تواند چند پاراگراف باشد</p>",
      "example": "<p>مثال اختیاری</p>"
    },
    "en": {
      "title": "Proof of Work",
      "short": "…",
      "body": "<p>…</p>"
    }
  }
]
```

**فیلدهای مستقل از زبان** (`id`، `tags`، `related`، `svg`) بیرون از بلاک‌های زبان قرار دارند تا بین دو زبان واگرا نشوند.

**فیلدهای داخل بلاک زبان:** `title`، `short` و `body` اجباری‌اند. `example` اختیاری است. `svg` اگر داخل بلاک زبان بیاید، جایگزین `svg` سطح بالا می‌شود — برای دیاگرام‌هایی که برچسب متنی دارند.

**دسته‌ی هر مدخل** از نام فایلی که در آن قرار دارد استنتاج می‌شود و **موضوعش** از نام پوشه؛ هیچ‌کدام داخل خود مدخل تکرار نمی‌شوند.

**`id` مدخل‌ها در کل سایت یکتاست، نه فقط داخل یک موضوع.** این تصمیم عمدی است و سه چیز را ساده نگه می‌دارد: آدرس مدخل `#/t/<id>` می‌ماند و موضوع را حمل نمی‌کند، `related` می‌تواند بدون نحو خاصی بین موضوع‌ها لینک بدهد، و اعتبارسنجیِ id تکراری همان چیزی است که هست. برای یک دانشنامه این محدودیت نیست بلکه ویژگی است: یک اصطلاح، یک مدخل.

**هشتگ‌ها** همیشه انگلیسی، با حروف کوچک و بدون `#` ذخیره می‌شوند و موقع نمایش `#` می‌گیرند. این‌طور یک هشتگ در هر دو زبان یکی است و فیلترش مشترک کار می‌کند.

### زبان ناقص

بلاک `en` اجباری نیست. اگر مدخلی فقط `fa` داشته باشد و کاربر روی انگلیسی باشد، به جای صفحه‌ی خالی، محتوای فارسی با نشان «ترجمه نشده» نمایش داده می‌شود و همان مدخل در فهرست انگلیسی هم دیده می‌شود.

## اعتبارسنجی

چون مدخل‌ها دستی اضافه می‌شوند، `data.js` بعد از لود این‌ها را بررسی می‌کند:

- `id` تکراری بین همه‌ی فایل‌ها
- فیلد اجباری جاافتاده (`id`، یا `title`/`short`/`body` در بلاک `fa`)
- عضوی از `related` که به `id` ناموجود اشاره می‌کند
- فایلی که در `categories.json` معرفی شده ولی وجود ندارد یا JSON نامعتبر دارد

هر خطا در یک نوار قرمز بالای صفحه با ذکر فایل و `id` مدخل نمایش داده می‌شود. سایت با وجود خطا بالا می‌آید و مدخل‌های سالم کار می‌کنند — خطا نباید کل صفحه را از کار بیندازد.

برای اینکه این تضمین واقعاً برقرار بماند، مدخلی که `fa.title` ندارد از خروجی `loadAll` حذف می‌شود. چنین مدخلی در هیچ نمایی قابل رندر نیست و استثنایش کل فهرست را سفید می‌کند. خطایش گزارش می‌شود ولی خودش رندر نمی‌شود. خطاهای نرم‌تر — `related` شکسته یا نبود بلاک `en` — مدخل را حذف نمی‌کنند و مدخل عادی نمایش داده می‌شود.

آخرین مورد (`related` شکسته) شایع‌ترین خطای این نوع پروژه است، چون مدخل‌ها در نوبت‌های مختلف اضافه می‌شوند و به مدخلی ارجاع می‌دهند که هنوز نوشته نشده.

## مسیریابی

مسیرها با hash:

| مسیر | نما |
|---|---|
| `#/` | فهرست |
| `#/t/proof-of-work` | صفحه‌ی یک مدخل |
| `#/tag/mining` | فهرست فیلترشده با یک هشتگ |
| `#/self-test` | صفحه‌ی خودآزمایی |

نتیجه: دکمه‌ی back مرورگر کار می‌کند و هر مدخل قابل بوکمارک است.

`id` ناشناخته در مسیر ← صفحه‌ی «مدخل یافت نشد» با لینک بازگشت به فهرست، نه صفحه‌ی سفید.

بالای هر مدخل breadcrumb: `فهرست ‹ اجماع ‹ اثبات کار`.

## فهرست

دو نما با یک دکمه‌ی تغییر:

- **موضوعی** (پیش‌فرض): مدخل‌ها زیر عنوان دسته‌شان، با شمارنده‌ی تعداد. دسته‌ها از `categories.json` می‌آیند.
- **الفبایی**: همه‌ی مدخل‌ها پشت سر هم بر اساس `title` زبان جاری. مرتب‌سازی با `localeCompare` و locale زبان جاری انجام می‌شود، چون ترتیب حروف فارسی با ترتیب کدهای یونیکد یکی نیست.

نمای انتخابی در `localStorage` می‌ماند.

زیر نام هر مدخل، `short` آن نمایش داده می‌شود تا بدون باز کردن صفحه بشود فهمید درباره‌ی چیست.

## جستجو و هشتگ

نوار جستجو بالای فهرست، فیلتر زنده با هر کلید. هم‌زمان در `title` و `short` هر دو زبان و در `tags` جستجو می‌کند — پس چه «اثبات کار» بزنی چه `proof`، مدخل پیدا می‌شود.

کلید `/` فوکوس را به نوار جستجو می‌برد. کلید `Escape` جستجو را پاک می‌کند.

هشتگ‌های هر مدخل زیر عنوانش نمایش داده می‌شوند و کلیک‌پذیرند؛ کلیک روی هشتگ به `#/tag/<tag>` می‌رود.

نتیجه‌ی خالی ← پیام «مدخلی یافت نشد» به‌همراه دکمه‌ی پاک کردن جستجو.

## زبان

کلید تغییر زبان در هدر. تغییر زبان این‌ها را عوض می‌کند:

- محتوای مدخل‌ها (بلاک `fa` یا `en`)
- متن‌های رابط کاربری از `i18n.js`
- `dir` و `lang` روی `<html>` بین `rtl`/`fa` و `ltr`/`en`

انتخاب زبان در `localStorage` می‌ماند. زبان پیش‌فرض فارسی است.

در حالت فارسی، اصطلاحات و کدهای انگلیسی درون متن باید با `dir="ltr"` محصور شوند تا جهت‌شان به هم نریزد.

## ظاهر

تم تاریک، با حال‌وهوای موضوع — بدون افکت تزئینی:

- پس‌زمینه‌ی تیره (حدود `#0d1117`)، متن با کنتراست کافی برای مطالعه‌ی طولانی
- رنگ تأکید فیروزه‌ای برای لینک‌ها و نام‌های انگلیسی
- فونت مونواسپیس فقط برای هش، آدرس و کد — نه برای متن عادی
- عرض ستون متن محدود (حدود ۷۰ کاراکتر)
- شبکه‌ی نقطه‌ای بسیار کم‌رنگ در پس‌زمینه
- دسته‌ها در نمای موضوعی به شکل بلاک‌های به‌هم‌زنجیرشده نمایش داده می‌شوند
- فونت‌های سیستمی؛ بدون فونت آنلاین

طراحی واکنش‌گرا: فهرست روی موبایل تک‌ستونه می‌شود و SVGها با `max-width: 100%` جا می‌شوند.

## تست

تست‌رانر برای این اندازه پروژه توجیه ندارد. به جایش مسیر `#/self-test` همه‌ی مدخل‌ها را در هر دو زبان رندر می‌کند و گزارش می‌دهد:

- هر مدخلی که موقع رندر خطا داد
- خروجی کامل `validate()`
- شمار مدخل‌ها به تفکیک دسته، و فهرست مدخل‌هایی که ترجمه‌ی انگلیسی ندارند

قبل از هر بار انتشار، این صفحه یک بار باز و بررسی می‌شود.

## اجرا و انتشار

اجرای محلی — یکی از این دو:

```
node serve.js          # سرور بدون وابستگی، داخل ریپو
python3 -m http.server 8000
```

`serve.js` یک سرور استاتیک کوتاه با `node:http` و `node:fs` است؛ هیچ پکیجی نصب نمی‌کند.

انتشار: push به شاخه‌ی اصلی ریپوی GitHub با Pages فعال روی ریشه. چون همه‌چیز ایستاست، هیچ مرحله‌ی build لازم نیست و محیط محلی عیناً همان چیزی است که منتشر می‌شود.

## افزودن یک مدخل

۱. فایل دسته‌ی مربوطه را در `data/entries/` باز کن (اگر دسته‌ی جدید است، فایلش را بساز و به `categories.json` اضافه کن).
۲. یک آبجکت با ساختار بالا اضافه کن.
۳. صفحه را باز کن؛ نوار قرمز اعتبارسنجی نباید ظاهر شود.

هیچ فایل دیگری دست نمی‌خورد. فهرست، جستجو، دسته‌ها و لینک‌های مرتبط همه از خود داده ساخته می‌شوند.

## خارج از دامنه

این‌ها عمداً ساخته نمی‌شوند:

- **فرم افزودن مدخل از داخل صفحه** — با روند کاری فعلی تداخل دارد و روی سایت ایستا جایی برای ذخیره ندارد.
- **برچسب سطح (مقدماتی/پیشرفته)** — تا وقتی تعداد مدخل‌ها کم است ارزشی ندارد. هشتگ همین کار را انعطاف‌پذیرتر انجام می‌دهد.
- **تصاویر رستری** — دیاگرام‌ها به صورت SVG درون‌خطی نوشته می‌شوند: سبک، قابل ویرایش، و در تم تاریک درست دیده می‌شوند.
